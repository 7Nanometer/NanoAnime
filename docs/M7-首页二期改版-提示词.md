## 一、红线（先读，最高优先级，一个都不许破）

参考站是**在线播放站**，本站承诺**「不提供在线播放，只跳转正版平台」**（页脚 + README + `CLAUDE.md` 第二节）。
**只借版式，不借内容。** 下面这些在参考站的三张截图里**都有**，本站**明确全部不要**：

- ❌ 「立即观看」「在线观看」「播放」按钮与播放图标（焦点位主按钮仍是**「去哪看」**→ `/anime/[id]#watch`）
- ❌ 卡片底部的 **「更新至 1 / 12」进度条**（new 截图里满屏都是）——暗示站内能看，**绝不照抄**
- ❌ **「18.4 万播放」「5.9k 次播放」这类播放量**（合集截图里每张卡片都有）——**绝不照抄**
- ❌ 「下载 App」入口、广告位招租、VPN 广告
- ❌ 任何把用户留在站内看片的交互

**新卡片元素的文案红线**（本轮新增两处，务必守住）：

| 参考图上的写法 | 本站改成 | 理由 |
|---|---|---|
| 「更新至 1 / 12」 | **一个字都不出现**。卡片底部仍用现成的 `getCardScheduleLabel(anime)`：在播 → 「周二 23:30」 | 报「下一集什么时候播」是资讯，报「更新至第 N 集」是暗示能看 |

其余照旧：前端不直连 AniList 只走 `/api/*`；第三方请求一律过 `lib/`；服务端缓存 ≥ 1h；
小字对比度 ≥ 4.5:1，**只用现有 OKLCH token，不新造灰**；空态/失败态必须真渲染；
动效受 `prefers-reduced-motion` 管辖。

## 二、动手前先拍板 5 个决策（**不要自己选，先问我**）

这几条是本轮真正的新增口径，也是唯一的风险点。**先给我方案 + 你的建议，我确认后再写代码。**

### Q1 「最近更新」页面的口径

- 路由：`app/updates/page.tsx`（顶栏标签「最近更新」）。
- 内容：**当季全部新番**，按最近更新排序。用现有 `useSeasonAnime` 就能拿到，**不用新接口**。
- 排序依据？我倾向 **`nextAiringEpisode.airingAt` 升序**（马上要更新的在最前），
  没有排期的（已完结/待开播）垫底，垫底段内按人气降序。
  备选：直接沿用接口返回的人气序（省事，但「最近更新」这个名字就名不副实了）。
- 页面用**全宽网格**（不是两行 14 部），这是「当季所有新番」的完整视图。
- ⚠️ 顶栏入口加了之后，`components/SiteHeader.tsx` 的 `NAV_ITEMS` 变 5 项——
  **必须在 320px 宽度上实测不溢出**（见验收 B7）。

### Q2 「铺满屏幕」到底改什么

用户原话「整体网页铺满整个网站屏幕」。现状是**三套不同的版心**，这是要先统一的：

| 位置 | 当前 | 
|---|---|
| 首页 `app/page.tsx` | `mx-auto max-w-6xl px-4` |
| 顶栏 / 页脚 | `mx-auto max-w-7xl px-4` |
| 焦点位 `HeroSpotlight` 图片 `sizes` | `(max-width: 1152px) 100vw, 1152px` ← **写死了 6xl 的宽度** |

建议做法（**注意这是改基础设施，影响全站，别只改首页**）：

1. 在 `app/globals.css`（或 `app/layout.tsx`）定义**一个版心常量**，
   顶栏 / 页脚 / 首页 / 后续新页面共用同一个值——现在是三处硬编码，迟早长歪。
2. 宽屏端放宽：`max-w-6xl`(1152) → **`max-w-[1440px]`**，
   两侧内边距在大屏加大（`px-4 sm:px-6 lg:px-8`），不要在 27 寸屏上留出两条巨大的黑边。
3. **焦点位不再受版心限制**：它是整宽视觉锚点，做成**真·全宽**（`w-screen` 或负 margin 抵消），
   里面的文字列再按版心对齐。参考站就是这样的。
4. ⚠️ `HeroSpotlight` 里那两处 `sizes` 属性必须跟着改（`1152px` → 新的最大宽度），
   否则浏览器会按旧宽度取图、宽屏上糊。
5. ⚠️ 改版心后**周表 7 列在 1440px 下会变宽**，得重看 `CalendarBoard` 的列内边距是否还合适。
6. **卡片尺寸**：一行 7 张是全新的断点需求。现有 `AnimeCard` 的 `sizes` 是
   `(max-width: 640px) 50vw, ..., 20vw`（按 5 列写的）。**加 7 列后要补/改 `sizes`**，
   否则浏览器按 20vw 取图，16px 的差距会让封面发糊。
   7 列建议断点：手机 2 列 / `sm` 3 / `md` 4 / `lg` 5 / **`xl` 7**。

### Q3 高分合集的评分口径（本轮最大的新能力）

现状：**全站只有 AniList 的 `averageScore`（0~100）**。
- Bangumi 评分：**没接**。`data/title-zh.json` 里存了 `bangumi_id`，
  但我实测**本机 Bangumi 的 DNS 被污染**（`api.bgm.tv` 解析到 `199.16.156.7`，挂代理也不通），
  拉评分这件事**只在离线脚本里能做，运行时绝不可能**（与中文名同一套纪律）。
- AniTrendz：**完全没接**，而且要抓网页、没有稳定 API。

**建议口径（等你确认）**：

- **v1 先只做 AniList 综合分**：`averageScore` 为主，
  但 AniList 的 `averageScore` 对**新番严重缺失**——我实测 2026 秋前 50 部里**只有 28 部有分**
  （新番刚播还没攒够评分）。所以高分合集**不能只从当季取**，要**跨季度取全年代高分榜**
  （`sort: SCORE_DESC`，这是我实测确认可用的排序）。
- **v2 再叠加 Bangumi**：写 `scripts/fetch-ratings.ts`，照 `fetch-title-zh.ts` 的模板
  （离线跑 + 存 `data/ratings.json` + 断点续跑 + 只增不减），
  从 `title-zh.json` 的 `bangumi_id` 反查 `api.bgm.tv/v0/subjects/{id}` 的 `rating.score`（10 分制 ×10 → 100 制）。
  **运行时只读文件**。
- **合成公式**：权重待你定。我倾向**等权 + 各自归一化**，
  并且**只在两个来源都有分时才做平均**，只有一个来源就用那一个（**不为缺分硬凑**）。
  界面上**标明分数来自哪几个站**，不假装是"全网综合"。
- **AniTrendz 建议不做**：抓网页维护成本高、没有稳定接口，收益不如把 Bangumi 接好。

**你要拍板的**：① 先做 v1 还是直接 v1+v2？② 权重怎么定？③ 缺分怎么显示（不显示分 vs 显示已有的那个）？

### Q4 高分合集的「卡片代表谁」+ 排序（**这条最容易做错，务必先定**）

我**已经用真数据跑过一遍探针**（高分榜前 100 部 + 按 `lib/series-graph.ts` 的 6 种白名单关系串图 3 轮），
实测结论如下，**这是定口径的事实依据**：

```
高分榜种子: 100 部 → 串图后池子 250 部
连通分量（合集）数: 54 个
size 分布: {1部:14, 2部:9, 3部:11, 4部:4, 5部:7, 6部:2, 7部:3, 8部:1, 10部以上:3}
按「合集均分」排序的前 10 名里，有 6 个是 size=1（就是单部作品）
取其前 7 个合集 = 只有 13 部作品
```

⚠️ **由此暴露三个必须你拍板的问题**：

1. **size=1 的"合集"算不算？**
   参考图里每张卡片都有「共 N 部」徽标（N≥2），说明参考站**只收 2 部以上的**。
   如果按这个口径，实测前 10 名会**掉到只剩 4 个**——21 张卡片根本凑不出来。
   所以要么**放宽**（允许 size=1 的也显示，只是不挂徽标），要么**降门槛**（均分取前 N 名之外再补）。
2. **「按合集均分排序」会让 size=1 的作品系统性地赢**：
   一部 91 分的孤独神作，均分就是 91；一个 8 部作品的系列，均分会被其中较弱的两部拉低。
   实测前 10 名里 6 个 size=1，就是这个机制造成的。
   **建议**：主排序用**合集均分**，但加一条**最低作品数约束**（例：size≥2 优先展示），
   或者给合集一个**规模加成**。这条我不敢自己定——它直接决定"高分合集"看起来像不像参考图。
3. **卡片显示哪张封面？** 建议：**合集里评分最高的那部的封面**，
   卡片下方第一行放**合集的中文名**（用它自己的名字，不是成员的），第二行放
   **「起始年份 · 评分 N」**（N = 合集均分）。
   ⚠️ 现有的 `AnimeCard` 是「一部作品 = 一张卡片」，合集不是 `Anime` 类型，
   **要么给 `AnimeCard` 加一个可选属性**（如 `collectionCount?: number` + 一个「共 N 部」徽标），
   **要么写一个 `CollectionCard`**。我倾向**加属性**——
   `AnimeCard.tsx` 头部写明「全站唯一的卡片组件，不要再建第二套」，加属性比第二套卡片安全。
   但合集卡片要显示的是**均分**不是单部评分，这个差异你得认一下。

**另外：21 部 / 三行 × 7 的口径**——首页只有 21 个卡片位，
所以是「**先聚合出合集 → 排序 → 取前 21 个合集**」，
**不是**「取前 21 部作品再聚合」。这两者结果完全不同，我按前者理解，确认一下。

### Q5 首页「新番」两行 14 部，取哪 14 部

## 五、交付方式

1. **先答 Q1~Q5**，给方案 + 你的建议，我确认后再动手。**不要跳过这一步直接写代码。**
2. 确认后**分三次收工**，每次都要能本地跑通：
   - 第一次：**A（版心）+ B（顶栏）+ C（新页面）** → 跑通 → 提交
   - 第二次：**D1 + D2 + D3**（焦点位 7 / 周表一行 / 新番 14）→ 跑通 → 提交
   - 第三次：**D4（高分合集）**——它依赖 Q3/Q4 的数据口径，
     如果走离线脚本，还要先跑一轮抓取 → 跑通 → 提交
3. ⚠️ **提交纪律（血泪，见进度第 141 条）**：
   - 每次提交前**在干净树上跑 `npm run build`**
   - 确认待推内容**在依赖图上闭合**（上次只推"视觉文件"，
     `app/layout.tsx` import 了别处组件 → Vercel `Module not found` 构建失败）
   - **两条线共用一个工作区时，`git add <目录>` 会扫入别人未提交的改动（不报错不提示）**——
     提交是整个工作区的动作，跨线并行要先约定提交时刻
4. 每次收工更新 `docs/进度.md`（**只追加/勾选，不删原文**），并**把 `docs/` 的改动一并提交**。
5. 提交信息用中文，说清做了什么。
