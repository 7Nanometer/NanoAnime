# NanoAnime番鉴 · 产品方案

> v1.0 ｜ 2026-09-29 ｜ 7Nanometer
> 应用名 **NanoAnime番鉴** ｜ 仓库名 `nanoanime`

---

## 一、一句话定义

**NanoAnime番鉴 是给中国动漫爱好者用的「追番 + 考据」社区。**

它不提供播放。它解决三件事：**看什么、追到第几集、去哪儿看正版**。

### ⚠️ 定位调整（2026-10-03）

**服务对象改为：自用 + 身边朋友使用**，不再面向公众运营。
（原有定位保留在上面 —— 很多设计是从"面向公众"推出来的，直接改写会丢掉依据。）

| 项 | 原定位（面向公众） | 现定位（自用 + 朋友） |
|---|---|---|
| ICP 备案 | 必需 | **不需要** |
| 内容审核 | UGC 必需（未接审核前关闭评论） | **不需要** → 「短评」可放回 |
| 上架 / 公开推广 | 目标 | 不追求 |
| 域名 / 国内可达性 | 硬需求 | **仍需要**（朋友也在国内），但紧迫性大幅降低 |
| 时间节奏 | 10-07 硬节点 | **硬节点失效** |

🔴 **不变的一条**：**不提供在线播放** —— 与用户规模无关。判决案例中小规模同样入刑（上海虹口"云×鹰"案：会员费共 17 万，判 3 年缓 3）。**用户少只影响量刑情节，不改变行为性质。**

**工程标准不降**：仓库是公开的，"求职作品集"这条线自动保留 —— 面试官照样看代码、提交记录与文档。

**后续影响**：M4（账号 + 云同步）照常完成；**M5（考据库 / 解析专栏）优先级提前** —— 自用 + 小圈子场景下，内容本身才是不可替代的价值。

## 二、为什么做这个

### 1. 需求是真的
追新番的人每周都在做一件重复的事：查今天更新什么、记住自己看到第几集、找个地方接着看。B 站有追番功能，但它只覆盖自家版权；Bangumi 有数据库，但产品体验停留在十年前。**没有人把「追番」这一件事认真做透。**

### 2. 合规是底线，也是护城河
盗版聚合站的内容不要钱，所以起量快——但它的成本随时会兑现（见 : 两高 2026 年典型案例，盗链传播 7.2 万部判 3–5 年 6 个月）。
本项目**只做元数据与跳转**：不接入任何盗版片源、不做解析接口、不绕过任何会员验证。播放动作只有一个 —— **跳到正版平台**。

这条约束看起来是劣势，实际是优势：**它让项目可以公开、可以上架、可以写进简历、可以长期运营。**

### 3. 做它的人对了
本项目作者本人是动漫深度解析博主（B 站 5 年、5800 粉、8 万赞）。这意味着：

- **冷启动流量现成**——不用从 0 拉用户
- **内容护城河现成**——考据与解析是爬虫爬不到的东西
- **第一用户就是作者自己**——需求判断不会跑偏

而且它是**双线合一**的：既是求职作品集，又是自媒体生产工具。

## 四、功能地图

### P0 · MVP（10-07 前完成，用于入职前演示）

1. **番剧库** — 搜索 + 详情（简介、集数、制作阵容、评分、系列关系）
2. **新番日历** — 周视图，今天/本周更新什么
3. **追番列表** — 加入 / 移除 / 状态标记（在看 / 看完 / 想看 / 弃番）
4. **观看进度** — 一集一打钩
5. **哪里能看** — 列出正版平台，点击跳转
6. **PWA** — 可安装到手机主屏

### P1 · 有用户之后（10-08 起，边实习边迭代）

7. **账号系统** — 登录 + 云同步（换设备不丢进度）
8. **评分与短评** — UGC 内容
9. **开播提醒** — Web Push
10. **年度报告** — 「我 2026 年看了 87 部番」——**这是最可能的传播引爆点**

### P2 · 内容沉淀期

11. **考据资料库** — 系列年表、staff 作品索引、原作对照
12. **解析专栏** — 作者本人的深度解析直接进 App
13. **社区讨论** — 按番剧分区的讨论区
14. **TV 大屏适配** — 遥控器交互

> **明确不做**：在线播放、盗版源聚合、解析接口、弹幕（审核成本过高）。

## 五、数据源

| 数据源 | 用途 | 授权 | 注意 |
|---|---|---|---|
| **AniList GraphQL** | 番剧元数据、海报、评分、**逐集播出时间** | 公开 API，免注册免 key | ⚠️ **不提供中文名**；限流 30–90 req/min（随服务状态变化），必须服务端缓存 |
| **Bangumi API** | **中文名**、中文简介、中文评分 | 公开 API | ⚠️ **国内已被墙，需代理**；只在离线补齐时调用，运行时不用 |
| ~~TMDB API~~ | ~~「在哪些平台能看」（watch providers）~~ | — | ❌ **中国大陆不可访问**（Jellyfin 官方文档列为已知不可访问的元数据源），且中国大陆观看渠道数据几乎为零 → **不采用** |

**落地策略**：AniList 为主库 → Bangumi 补中文 → TMDB 补观看渠道。

### ⚠️ AniList 没有中文字段

它的 `title` 只有 `romaji / english / native / userPreferred`，其中 `native` 是**作品原生语言**（日番即日文）。`synonyms` 偶尔带中文别名，但不可靠。

**结论：中文名必须从 Bangumi 取。这是必经项，不是可选优化。**

### 中文名配对策略（M1 执行，M0 不做）

1. 用 AniList 的 `title.native` + 首播年份，调 Bangumi 搜索接口
2. 命中则记录 `bangumi_id` 与 `title_zh`
3. **匹配失败一律留空，不猜**——名字写法有差异时会错配，宁缺勿错
4. **做成离线批量脚本，结果落成文件**（`data/title-zh.json`：`anilist_id → { bangumi_id, title_zh }`），并提交进 git

🔑 **为什么必须离线**：Bangumi 国内已被墙。补齐时挂代理跑一次，**补完的数据进代码库，之后任何环境都能用**——Bangumi 挂掉、改接口、加墙，都不影响产品运行。这是本项目对外部依赖的通用纪律（见宪法第五节第 6 条）。

### 实测结果（2026-09-30）

**全季 18/20 配上，抽查 10 部全对。**

配不上的两类，**暂不修**：

- Bangumi 把系列名挪到后面（如「ジョジョの奇妙な冒険」）
- Bangumi 多了「劇場版」前缀

理由：**不配 > 错配**。剥离前后缀再搜，可能把剧场版配成 TV 版的中文名——风险大于收益。这两张卡片退回日文原名 + 英文名，不空、不错。

### 中文搜索的覆盖范围（扩充排在 M5）

**已实测：AniList 完全没有中文索引** —— 把本地表里 18 个中文名逐个喂给它的搜索接口，**命中 0**。（偶尔搜「药屋」两个字能中，是因为日文里也有这两个汉字，属撞大运。）

**所以中文搜索只能靠本地这张表——不是"保险做法"，是"唯一做法"。**

当前表只覆盖本季 20 部 → **中文搜索只能命中这 18 部**（搜索页已如实提示用户）。

扩充方案（**M5 做，不要插在 M1–M3 期间**）：

- 脚本参数化 `--scope=season|top2000|all`
- 先跑 **top2000**（AniList 按 popularity 排序），覆盖绝大多数搜索需求
- 落盘结构不变，文件约 200 KB，可接受
- **等上线后有真实用户数据再决定要不要全量** —— 比现在盲目拉取更经济

### 图片加载（已实测 09-29 / 修订 09-30）

AniList 图床 `s4.anilist.co` 国内直连实测 **3.7s / 3.7s / 16.2s**。Next 内置图片优化器有 **7 秒硬超时**（无配置项可改），超时即返回 500。

**这不是图片坏了，是"第一次抓太慢被掐断"**——图一旦抓到即被缓存，二次请求 0.003s。
**补测**：本机挂代理后刷新，**20/20 全部加载成功** → 坐实是本机到 AniList 的连接问题，非代码或配置问题。

⚠️ **09-30 修订：Bangumi 已在国内被墙**（`bgm.tv` / `lain.bgm.tv` 需代理），**原「M1 换 Bangumi 图床」方案作废**。

| 阶段 | 方案 |
|---|---|
| **本地开发** | `images.unoptimized` 在 development 下为 true —— 浏览器直连图床，绕开 7 秒超时。配合代理使用 |
| **M0 ~ M3 线上** | **保持 Next 图片优化 + AniList 图床不动**。Vercel 服务器在海外，抓 AniList 快，不存在超时 |
| **长期（迁国内服务器后）** | 自建图片缓存：同步时把封面抓到国内对象存储，运行时零外网依赖 |

⚠️ **部署地决定图床选择**（Next 优化器由部署服务器去抓图）：

| 部署地 | 抓 AniList（海外） | 抓 Bangumi（国内，现已墙） |
|---|---|---|
| Vercel（海外） | 快 ✓ | 慢 / 不通 |
| 国内服务器 | 慢 | 需代理 |

**结论：Vercel 阶段不换图床。** 等迁到国内服务器时，再连同数据源一起本地化。

⚠️ **M3 验证项（尚未实测）**：「Vercel 服务器抓 AniList 快」是从部署位置**推断**的，没有实测。M3 上线后第一件事就是验证——若同样慢，方案需重做。

⚠️ **别混淆两件事**：本地开发图慢 = 本机到图床的连接慢；线上用户图慢 = 用户到部署地的连接慢。**成因不同，解法不同。**

## 六、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | Next.js（App Router）+ TypeScript | 一套代码覆盖浏览器/手机/TV 浏览器/PWA；求职市场认知度最高 |
| 样式 | Tailwind CSS + shadcn/ui | 出效果快，AI 辅助生态最成熟 |
| 数据获取 | TanStack Query | 客户端缓存，减少重复请求 |
| 后端 | Next.js Route Handlers | 代理 AniList、藏 key、统一缓存；无需独立服务器 |
| 数据库 | Supabase（Postgres） | 免运维、自带 RLS 行级权限 |
| 认证 | Supabase Auth | 邮箱/手机号/第三方登录开箱即用 |
| 部署 | Vercel | 免费额度足够，push 即上线 |
| 可安装 | next-pwa | 一行配置变「App」 |

**为什么是这套**：Web/PWA 一套全端，正好是选定的首端策略；技术栈全是当前招聘市场上被认的；且 AI 辅助写起来顺（生态大、报错好搜）。

⚠️ **可迁移性约束**：为了将来能把整个应用搬到国内服务器，**不使用 Vercel 专有服务**（Vercel KV / Blob / Edge Config）。数据层只用 Supabase，应用保持标准 Next.js Node 形态。

## 七、数据模型

```sql
-- 番剧主表：AniList 数据的本地缓存
create table anime (
  id             bigserial primary key,
  anilist_id     int unique not null,
  bangumi_id     int,
  title_native   text not null,        -- 日文原名
  title_zh       text,                 -- 中文名
  title_en       text,                 -- 英文名
  cover_url      text,
  banner_url     text,
  synopsis       text,
  format         text,                 -- TV / MOVIE / OVA / ONA
  season         text,                 -- WINTER / SPRING / SUMMER / FALL
  season_year    int,
  total_episodes int,
  status         text,                 -- RELEASING / FINISHED / NOT_YET
  average_score  numeric(4,1),
  popularity     int,
  genres         text[],
  studios        text[],
  updated_at     timestamptz default now()
);
create index on anime (season_year, season);
create index on anime (status);

-- 剧集表：日历与进度都依赖它
create table episode (
  id        bigserial primary key,
  anime_id  bigint references anime(id) on delete cascade,
  number    numeric(6,1) not null,     -- 支持 12.5 集这类特殊编号
  title     text,
  airs_at   timestamptz,
  unique (anime_id, number)
);
create index on episode (airs_at);

-- 用户扩展信息（账号本身由 Supabase Auth 托管）
create table profile (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  nickname   text,
  avatar_url text,
  created_at timestamptz default now()
);

-- 追番记录 + 观看进度
-- ⚠️ M4 实际建的就是这一张（2026-10-03 定）：user_id 直指 auth.users，anilist_id 不建外键。
--    理由见本节末「建表范围」。
create table collection (
  id          bigserial primary key,
  user_id     uuid references auth.users(id) on delete cascade,
  anilist_id  int not null,             -- AniList 番剧编号（不建外键）
  status      text not null default 'watching',  -- watching/completed/planning/paused/dropped
  progress    int default 0,
  score       numeric(3,1),
  is_favorite boolean default false,
  note        text,
  -- 快照字段：M2-2 定的「加入追番时顺手存一份」，AniList 抖动时 /my 也能正常显示
  title_snapshot          text,
  title_zh_snapshot       text,
  cover_url_snapshot      text,
  total_episodes_snapshot int,
  started_at  date,
  finished_at date,
  updated_at  timestamptz default now(),
  unique (user_id, anilist_id)
);

-- 短评
create table comment (
  id         bigserial primary key,
  user_id    uuid references profile(user_id) on delete cascade,
  anime_id   bigint references anime(id) on delete cascade,
  content    text not null,
  status     text default 'pending',   -- pending/approved/rejected，先审后发
  created_at timestamptz default now()
);

-- 正版观看渠道（is_official 恒为 true：非正版不收录）
create table streaming_link (
  id          bigserial primary key,
  anime_id    bigint references anime(id) on delete cascade,
  platform    text not null,           -- bilibili / iqiyi / tencent / netflix / crunchyroll
  region      text default 'CN',
  url         text not null,
  is_official boolean default true
);
```

**权限（RLS）**：`profile` / `collection` / `comment` 全部开启行级策略，`user_id = auth.uid()`；`anime` / `episode` / `streaming_link` 对所有人只读，仅服务端可写。

### 建表范围（2026-10-03 修正）

上面那张是**目标结构**，不是一次建完 —— 现在只建 `collection` 一张。

| 表 | 何时建 | 说明 |
|---|---|---|
| **collection** | **M4（本次）** | M4 需要的唯一一张表 |
| anime / episode / streaming_link | **M5 及以后** | 番剧数据现在仍在 AniList 侧（本地只有 18 条中文名，不是全量）。**现在建了是空表，用不上** |
| profile | **暂不建** | 它只存昵称 / 头像，而 M4 不做个人资料页；账号信息 Supabase 自带的 `auth.users` 已有 |
| comment（短评） | **暂不建** | 公开 UGC，国内上线需内容审核 → 推迟到 M5 |

**为什么 `collection` 不建外键 —— 这不是妥协，是更正确的设计：**

1. **`anime` 表是「镜像 / 缓存」，不是「事实来源」** —— 事实来源是 AniList。若要求外键引用，等于规定"没有 anime 记录就不能追番"，凭空引入一个强耦合：同步追番得先同步番剧，而番剧同步的覆盖范围（本季 / 全量）还没定。
2. **外键会直接卡死 M4-2** —— `anime` 现在是空表，插 `collection` 记录会当场违反外键约束。
3. **快照自包含已被实测验证** —— M2-2 时模拟 AniList 挂掉，`/my` 照样显示、进度一条没少。**存快照比依赖 join 更稳。**

> 代价（已记下）：`collection.anilist_id` 与将来的 `anime.anilist_id` 靠约定对齐，没有数据库层约束。若哪天真建 `anime` 表，可能要补一次数据校验。

## 十、合规清单（上线前逐项打钩）

- [x] 不接入任何盗版片源
- [x] 不做解析接口、不绕过任何会员验证
- [x] 播放动作仅限跳转正版平台
- [x] 元数据来源标注（AniList / Bangumi），**只在页脚以小字呈现，不做成跳转链接** —— 避免把来源做成导流入口
- [x] 海报使用官方公开资源，标注版权归属
- [x] **不抓取第三方新番站的编排数据、不盗链其图床** —— 图源只用开放 API 提供的官方资源
- [ ] UGC 短评必须有审核机制（关键词过滤 + 举报 + 人工复核），**未完成前先关闭评论功能**
