## 已裁定事项（实现前必读）

| 项 | 裁定 |
|---|---|
| **制作人员取几页** | **2 页 / 50 条**（一次请求内用别名取，**不增加请求数**，3KB → 6KB）。理由：2 页正好覆盖音乐 / 主题歌 / 制片人这一档 |
| **制作人员是否折叠** | **不折叠、全列**。折叠默认值若 < 26 会藏掉音乐（进击反例），给到 30+ 又与全列无异 |
| **制作人员的标注** | **「仅列出主要制作人员，非完整名单」** —— 后半句不能省 |
| **无声优的角色** | **不进名单** + 区块底部小字「另有 N 个角色暂无声优资料」。**静默消失算失败，数字必须出现** |
| **名字说明位置** | **制作人员 / 声优两块底部各一行**（区块可能单独为空，说明不能只挂一块） |
| **人名是否链接** | **本轮不是链接**。**不接受「点了跳 404」**，宁可不可点 |

✅ **实测（2026-10-06）：这条抓到了一个真 bug** —— 只过滤关系类型不够，年表里冒出了「2022 MANGA 魔法使いの夜」「2026 NOVEL 魔法使いの夜」。**修法：关系边必须带 `nodeType`，两个条件都查。**
> 这就是「一条抵两条」的价值：若当初只写「验白名单生效」，这个 bug 会漏到线上

**B4 只剩自己一部时不显示区块**

预期：都没有「系列年表」这一块

**B5 超过 12 部折叠**（※16 部）
怎么验：`/anime/16498`
预期：默认 12 行，末尾按钮「展开全部 16 部」
⚠️ 这条能抓出一个真会犯的错：进击**直接相连过滤后只有 8 条，串完才 16 部**。若用"直接关系数"决定折叠，这条就挂

**B6 点击展开**
怎么验：点按钮
预期：16 行全显示、按钮消失、不刷新不跳转

**B7 键盘可达**
怎么验：刷新后 Tab 到按钮，按 Enter；再试空格
预期：两种都能展开

**B8 没有 JS 也能看到前 12 行**
判据：`curl -s http://localhost:3000/anime/16498` 拿到的 HTML 里**同时有 SSR 的 DOM 和 RSC payload**（`<script>self.__next_f.push(…)` 里的 JSON）。payload 里带着全部 16 条标题 —— **直接 grep 标题会假阳性通过**，无论前端渲染了几行。
所以判据是：**剥掉所有 `<script>…</script>` 之后再数**，剩下的才是浏览器跑 JS 前真正画出来的东西。
```
curl -s .../anime/16498 > page.html
剥掉 <script> 块后，在年表那个 <ol> 里数 <li> 的个数
```
预期 ≥12
**正对照（必做，否则等于没验）**：同一份 HTML **不剥 script** 时，标题出现次数应**明显多于**剥掉后的。若两者相同，说明这份 HTML 里根本没有 payload，**判据失效、结论不算数**

**B9 ≤12 部时不出现按钮**（※9 部）
怎么验：`/anime/5114`（钢炼 FA）
预期：9 行全显示，没有按钮
（原写「11 部」是定稿前旧口径的测量值；正式裁定是 6 类关系，实测 9 部）

## ⚠️ 通用纪律：不要在界面上说「共 N 个」

**背景**：这是本项目**第三次"文案与事实不符"**，而且机制最隐蔽：

| 第几次 | 机制 |
|---|---|
| 页脚隐私声明（M4-2） | **功能变了，承诺没跟着变** |
| 灵笼空态（本轮） | 陈述本身是错的（「还没有登记角色」，实际有角色） |
| 灵笼数字（本轮） | **把技术上限当成了业务事实** —— 不是"忘了更新"，是**错误地相信了接口返回的数量** |

**规则**：凡是要在界面上说「共 N 个」「N 部」「N 人」的地方，**先确认这个 N 是怎么来的**。
- 如果它是**从分页结果数出来的** → **不成立**（`pageInfo.total` 已被证明不可信：恒返回 5000 / 翻不同页给不同数；嵌套连接还静默截断在 25）
- 正确做法：**「仅列出…，非完整名单」这种"说范围不说数量"的措辞**

**对照检查（现有文案）**：
- ✅ **C4**「仅列出主要制作人员，非完整名单」—— 不写数字，**正确**
- 🔧 **D2 / D6** —— 改前带数字，**已改为不带**
- 🔧 **F4 顶到上限时的按钮文案**：「展开全部 73 部」 + 降级小字「没抓全」**自相矛盾** → 已改为「**展开已抓到的 73 部**」
- 🔴 **首页「2026 年秋新番 · 共 20 部」—— 漏网的一处**：那个 **20 不是"本季共 20 部"，是我们主动取的人气前 20**（每季实际 50+ 部）。**「共」字会让用户以为本季只有 20 部** → 应改为「**人气前 20**」或同类（说清"这是我们取的前 20"）
  > 与灵笼那句是**同一个错**：把「我们取了 N 条」当成「一共 N 条」说出去。只是这次的 N 来自**我们自己的查询上限**，不是接口的截断上限
- ✅ **其余带数字处成立**（它们的 N 是"本屏实际显示了什么"）：
  - 日历「本周共 82 集」= 本周**有排期**的集数（已翻页取全）
  - 我的追番「共 N 部」= 本地记录数
  - 剧集列表「共 1147 集，**此处只列出有排期数据的 94 集**」—— **说清了范围**，正确
  - 搜索页「只显示前 24 条，可用更具体的关键词缩小范围」—— 正确

**D5 没有无声优角色时，那行小字不出现【审补充】**
背景：D2 验的是「有 4 个无声优」的情况。而**声优配齐率是老番 96.7%、主角档 100%** —— 「所有角色都有声优」是**真会触发的状态**。
怎么验：找一部**全部角色都有声优**的番（进击 16498 是否如此，先确认；不是就另找）
预期：**底部不出现那行小字**（不能写死成「另有 0 个角色暂无声优资料」）
⚠️ 如果实现把这行字写死，D2 会通过、这条会挂 —— 两条合起来才验得全

## 实现阶段的参数变更（2026-10-06）

| 参数 | 原值 | 改为 | 依据 | 影响的验收 |
|---|---|---|---|---|
| **年表补抓轮数上限** | 4（**拍脑袋定的**） | **8** | 实测进击需 **7 轮** —— 系列是链式结构（S1→S2→S3…），**每轮只走一层，轮数 ≈ 链长**。原值 4 导致进击永远挂着「没抓全」 | **A3、F4、G1** |

⚠️ **参数变更后，这三条必须重跑** —— 报告里 F4 写明「正好停在 4 轮（**当时的上限**）」= 旧参数下的验证。

**上限 8 的余量（2026-10-06 抽样实测，5 部长链系列）**：

| 系列 | 轮数 | 年表部数 | 结论 |
|---|---|---|---|
| 機動戦士ガンダム（UC 线） | 6 | 121 | ✅ |
| 化物語（物语系列） | **8** | 19 | ✅ 用满但不超 |
| **Fate/Zero** | **10** | 44 | ⚠️ **超 8**，应用里会走降级 |
| ドラゴンボール | 5 | 43 | ✅ |
| 名探偵コナン | 2 | 66 | ✅（星形） |

→ **8 轮在 5 个样本里 4 个够用**；Fate 这类"多分支 + 长尾"的会超。
→ **超了的表现就是那行降级小字，页面不坏**（这正是 F1/F4 两套降级存在的意义）—— **但按钮文案要按 F4 的新要求改**。
→ 另记一个自愈行为：**单轮最多取回 50 部**，超过 50 个 id 时剩下的自动落到下一轮（柯南第 1 轮要 62 个 → 回 50，第 2 轮补齐）。

### 未采纳的备选（记档，不做）

**嵌套查询减轮数**：GraphQL 可嵌套 `relations.node.relations.node…`，一次拿多层 → 7 轮可压到 2–3 轮。
**现在不做**：当前每冷启 ~9 次请求、缓存 24 小时，对「自用 + 朋友圈」规模余量足够；嵌套会引入深度限制等未知风险。**将来若限流吃紧再考虑。**
